## EC-2 — 캐시 자정 경계 (23:58 → 00:03 KST)

### 현상

캐시가 KST 자정 직전에 기록되면 TTL 내에 새 날짜가 시작되어도 어제 날짜의 응답이 서빙된다.

```
23:58 KST 캐시 기록: days[0].date = "2026-04-29", TTL +5분
00:01 KST 캐시 HIT:  days[0].date = "2026-04-29"  ← KST 기준 어제
```

### #8 수정 전 vs 수정 후

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 날짜 라벨 오류 구간 | 매일 00:00~08:59 KST (9시간) | 최대 00:00~00:05 KST (5분) |
| 원인 | UTC `toISOString()` 상시 오류 | 캐시 TTL 내 stale |
| OW 데이터 오염 | 동시 발생 | 없음 (KST 필터 적용된 데이터가 캐시됨) |

### 잔존 리스크

- **발생 확률:** 캐시가 자정 직전 5분 이내 기록될 때만 발생 = 5분 / 24시간 ≈ **0.35%**
- **심각도:** 낮음 — 5분간 어제 예보를 오늘로 제공
- **실용적 허용 여부:** 날씨 앱 기준 자정 직후 5분 stale은 허용 가능한 수준

### 해소 방안 검토

캐시 키에 KST 날짜를 포함(`"seoul:3:2026-04-30"`)하면 이론상 해소된다.  
단, 현재 `Map` 기반 캐시는 능동 eviction이 없다. 자정마다 구 키가 누적되면 메모리 누수가 발생한다.  
TTL 5분이 사실상 자정 경계를 덮으므로 **현재 설계가 합리적인 트레이드오프**로 결론.

## CC-5 — `days=2` 캐시 독립 엔트리

### 현상

`days=3` 캐시가 존재해도 `days=2` 요청은 별도 키(`"seoul:2"`)로 항상 캐시 MISS가 발생한다.  
`days=2` 데이터는 `days=3`의 완전한 부분집합이지만 캐시가 이를 인식하지 못한다.

### 리스크 평가

- **데이터 정확성:** 없음 — fresh fetch이므로 정확도는 오히려 유리
- **실질 비용:**
  - 중복 upstream 호출: `days=1/2/3` 각각 독립 요청 시 provider 최대 3회 중복
  - OW 무료 플랜 한도(1,000 calls/day) 소진 가능성 — 현재 트래픽에서는 무해

### 해소 방안 검토

`days=3` 캐시에서 앞 N개를 슬라이스해 `days=1/2`에 재사용하는 계층이 필요하다.  
구현 복잡도 대비 현재 트래픽 규모에서 이득이 없다.  
OW 호출 한도에 실제로 근접할 때 대응하는 것이 적절하다.

## 파생 논의 1 — 5분 TTL의 적절성

### 사용자 관찰

> "익일 예보는 실시간으로 안 바뀌지 않나? 이틀 뒤, 삼일 뒤는 바뀔 수 있는데, 매 요청마다 provider에 요청할 필요가 있냐."

### 분석 및 동의

세 provider 모두 NWP(수치예보 모델) 기반이며 모델 갱신 주기는 약 6시간이다.

| Provider | 모델 갱신 주기 |
|---|---|
| OpenWeather | GFS 기반, 00:00 / 06:00 / 12:00 / 18:00 UTC |
| WeatherAPI | 동일 계열, ~6시간 |
| Open-Meteo | GFS + ICON + ECMWF, ~6시간 |

현재 TTL 5분 → 시간당 12회 호출 → 6시간 동안 72회 동일 데이터 반복 수신.

예보 지평별 변동성:

| | 오늘 (day[0]) | 내일 (day[1]) | 모레 (day[2]) |
|---|---|---|---|
| 분 단위 변동 | 없음 | 없음 | 없음 |
| 모델 실행 간 변동 | 낮음 | 중간 | 높음 |
| 적정 캐시 TTL | 15~30분 | 30~60분 | 60~120분 |

`/api/weather/current`(실시간 기온)은 5분이 적절하지만, `/api/weather/forecast`(일별 요약)는 5분이 과도하게 짧다.

### 결론 (동의)

**forecast 캐시 TTL을 30분으로 상향**하면 코드 한 줄 변경으로 provider 호출을 ~6배 줄이면서 데이터 품질 저하가 없다.

```typescript
const CURRENT_CACHE_TTL_MS  = 5 * 60 * 1000;   // 5분 — 실시간 기상
const FORECAST_CACHE_TTL_MS = 30 * 60 * 1000;  // 30분 — 일별 예보
```

구현은 별도 이슈로 처리 예정.

## 파생 논의 2 — 파일 형태 저장으로 비정상 데이터 대응

### 사용자 제안

> "프록시 서버가 파일 형태로 데이터를 가지고 있으면 비정상 데이터 유입 같은 예외 케이스로 인한 UI 출력 오류를 예방할 수 있지 않을까."

### 반박

**① 파일 시스템이 존재하지 않는다**

Cloudflare Workers는 V8 isolate 런타임이다. `fs` 모듈과 디스크 I/O가 샌드박스로 차단돼 있어 파일 저장 자체가 불가능하다.

**② "파일 동등물"인 KV/R2는 네트워크 호출이다**

| | in-memory Map | Cloudflare KV | Cloudflare R2 |
|---|---|---|---|
| 읽기 지연 | ~0ms | 1~50ms | 10~100ms |
| 전역 일관성 | isolate 내 즉시 | 최대 60초 지연 | 즉시 |
| 추가 비용 | 없음 | 있음 | 있음 |

캐시 조회마다 50ms가 추가되면 전체 응답 지연이 증가한다.

**③ 비정상 데이터 차단은 저장 위치가 아닌 검증 레이어 문제다**

저장 매체를 바꿔도 비정상 데이터가 그대로 저장된다.

```
provider → (temp=9999) → KV 저장 → UI 출력 오류  ← 해결 안 됨
provider → (temp=9999) → 범위 검증 실패 → 차단    ← 올바른 접근
```

### 유효한 핵심 (동의)

파일 저장 아이디어의 본질은 **last-known-good 패턴**이다. 이는 별도로 유효하다.

```
정상 흐름: provider → 검증 통과 → KV 갱신 + 응답
비정상 흐름: provider → 검증 실패 → KV last-known-good 서빙
```

단, 이는 TTL 최적화와 독립된 문제이며, 현재 규모에서 구현 비용 대비 발생 빈도를 먼저 확인해야 한다.

## 파생 논의 3 — OW 오류 사례와 비정상 데이터의 관계

### 사용자 참조

방안 2 리스크 분석에서 언급한 OW 오류 사례:
> "2023년 OW API v2.5에서 일부 도시의 `city.timezone` 필드가 `0`으로 반환된 커뮤니티 보고 사례"

### 정정

이 버그는 **`city.timezone` 메타데이터 필드**의 오류다.

현재 구현(방안 1, `KST_OFFSET_SEC` 상수)은 `city.timezone` 필드를 읽지 않는다.  
따라서 해당 버그는 현재 시스템과 **무관**하다.

이 사례를 "비정상 데이터 유입 → UI 오류"의 근거로 쓰는 것은 맥락이 다르다.

### 현재 시스템에 실제로 영향을 줄 수 있는 비정상 케이스

| 케이스 | 현재 처리 | UI 영향 여부 |
|---|---|---|
| `temp = 9999` 같은 값 범위 이탈 | 검증 없이 집계에 포함 | **있음** — 이상값이 가중평균에 반영 |
| `list[]` 빈 배열 | `null` 반환 → weight 재분배 | 없음 |
| 필수 필드(`dt`, `main.temp`) 누락 | 런타임 에러 가능 | 503 반환 |
| 완전히 다른 도시 좌표 응답 | 탐지 불가 | 잘못된 도시 데이터 |

사용자가 말한 "비정상 데이터 → UI 출력 오류"에 실제로 해당하는 케이스는 **값 범위 이탈**이다.  
이는 normalizer 레이어의 범위 검증으로 막아야 하며, 저장 매체 변경으로는 해결되지 않는다.
